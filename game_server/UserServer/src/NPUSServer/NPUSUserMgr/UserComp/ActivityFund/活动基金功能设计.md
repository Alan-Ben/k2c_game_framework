# 活动基金功能设计文档

## 1. 功能概述

活动基金是一个类战令系统的功能，**支持活动基金和常驻基金两种模式**，玩家通过完成任务获得分数，分数达到指定值后可以升级基金阶段，并领取对应阶段的奖励。

### 核心机制

- **双模式支持**：
  - **活动基金**：与活动实例绑定，有活动实例ID
  - **常驻基金**：独立于活动系统，活动实例ID为0
- **双档奖励**：每个阶段有免费档和付费档两种奖励
- **分数累计**：玩家完成任务获得分数，分数不会被消耗，只用于判断是否可以领取奖励
- **阶段系统**：通过配表 `activity_fund_step` 定义阶段和升级所需分数，服务器根据当前分数自动计算阶段
- **等级与凭证道具**：阶段按等级分组，每个等级有独立的凭证道具（`distinguish_item`），玩家需要拥有对应等级的凭证道具才能领取该等级的付费档奖励
- **任务分组复用**：通过任务组机制，多个基金可以共享同一套任务配置
- **一键领取**：客户端请求领取时，自动领取所有满足条件的阶段奖励

## 2. 数据表结构

### 2.1 activity_fund（主表）

| 字段                             | 类型     | 说明                                    |
|--------------------------------|--------|---------------------------------------|
| fund_id                        | long   | **基金ID（主键，唯一标识）**                     |
| activity_id                    | long   | **活动ID（0表示常驻基金）**                     |
| task_group_id                  | long   | **任务组ID（关联任务分组）**                     |
| activity_fund_name             | string | 基金名称                                  |
| gift_pack_id                   | int    | 付费礼包ID                                |
| task_refresh_time              | int    | 任务刷新时间（秒），0表示不刷新                      |
| process_cur_count              | string | 计数器的高级公式(ENPPlayerVariableType)       |
| refresh_process_cur_count_type | string | 刷新高级公式的事件枚举                           |

**重要变更**：
- `fund_id`：新增，作为基金的唯一标识（主键）
- `activity_id`：改为可选，0 表示常驻基金，非0表示活动基金
- `task_group_id`：新增，通过任务组ID关联任务，多个基金可共享同一任务组
- `task_refresh_time`：新增，任务刷新时间（秒），配置后支持任务轮次刷新机制

### 2.2 activity_fund_step（阶段表）

| 字段                    | 类型     | 说明              |
|-----------------------|--------|-----------------|
| id                    | long   | 唯一ID            |
| **fund_id**           | long   | **基金ID（外键）**    |
| step                  | int    | 阶段              |
| need_count            | int    | 领取所需分数          |
| free_reward_item_list | string | 免费档奖励           |
| pay_reward_item_list  | string | 付费档奖励           |

**重要变更**：
- `activity_id` → `fund_id`：改为使用基金ID关联
- `need_count`：玩家的当前分数需要 >= 此值才能领取
- 阶段按分数递增排列，分数达到某阶段后自动解锁该阶段奖励

### 2.3 activity_fund_level（等级表）

| 字段                 | 类型     | 说明                      |
|--------------------|--------|-------------------------|
| id                 | long   | 唯一ID                    |
| **fund_id**        | long   | **基金ID（外键）**            |
| level              | int    | 等级号                     |
| last_step          | int    | 该等级的最后一个阶段（-1表示无上限）    |
| distinguish_item   | string | 凭证道具（拥有此道具可领取该等级的付费档） |
| activate_exp_count | long   | 激活该等级时获得的经验值          |

**逻辑说明**：
- `fund_id`：关联基金，每个基金有独立的等级配置
- `last_step = -1`：表示无上限等级，允许无限扩展
- `distinguish_item`：按等级配置凭证道具，支持分级售卖
- `activate_exp_count`：购买凭证道具激活该等级时，自动增加的经验值，会影响当前阶段计算

- `activity_id` → `group_id`：改为使用任务组ID，支持任务复用

## 4. 业务逻辑说明

### 4.1 初始化流程

1. 玩家登录时，服务器加载玩家的活动基金数据
2. 通过 `GS2GC_002_083_RetActivityFundInit` 推送所有活动基金信息给客户端
3. 包含：公式分数、任务分数、已领取最大阶段等

### 4.2 任务完成流程

1. 玩家触发任务相关事件
2. 服务器监听事件并判断触发条件（`trigger_condition`）
3. 根据 `trigger_count_rate` 计算增量值
4. 更新任务计数（增量或覆盖模式）
5. 任务计数达到要求时，任务完成次数+1，重置计数
6. 将获得的分数（`gain_score`）添加到任务分数
7. 推送 `GS2GC_017_064_OnActivityFundScoreChg` 更新分数

### 4.3 一键领取流程

1. 客户端发送 `GC2GS_017_018_ReqActivityFundDrawStepReward`
2. 服务器校验：
    - 活动基金是否存在
    - 是否有可领取的阶段（当前阶段 > 已领取阶段）
3. 计算可领取区间：`[已领取最大阶段+1, 当前可达阶段]`
4. 获取所有等级配置（已按level排序）
5. **按等级遍历**，找到第一个未领完的等级：
    - 检查当前等级是否完成（必须免费档和付费档都领完才算完成）
    - 如果已完成，继续下一个等级
    - 如果未完成：
      - 计算该等级包含的阶段范围
      - 计算该等级下可领取的阶段范围
      - 获取该等级下的所有阶段配置
      - 遍历阶段收集奖励：
        - **免费档**：直接收集奖励
        - **付费档**：根据该阶段所属等级的凭证道具判断
          - 有对应等级的凭证：收集付费档奖励
          - 无对应等级的凭证：跳过付费档
      - **处理完后结束**（不继续处理下一个等级）
6. 发放所有奖励（通过 `gainItemList`）
7. 更新已领取阶段记录（保存最大阶段号）
8. 推送 `GS2GC_017_066_OnActivityFundDrawRewardChg` 更新领取状态
9. 奖励通过 `GS2GC_007_050_OnGainItems` 推送

**重要**：
- 一次只处理一个等级，确保玩家按等级顺序推进
- 购买凭证道具后，激活经验值会在下次计算总分时自动生效（通过 `getTotalScore()` 动态计算）

### 4.4 阶段计算逻辑

- **不需要存储阶段字段**，通过配表实时计算
- 根据 `totalScore` 和 `activity_fund_step` 表计算当前阶段
- 示例：
  ```
  step 1: score >= 100
  step 2: score >= 300
  step 3: score >= 600
  ```
  如果玩家 score = 500，则当前阶段为 2

### 4.5 公式分数刷新

- 公式分数通过 `process_cur_count` 配置的公式计算
- 当 `refresh_process_cur_count_type` 指定的事件触发时，重新计算公式分数
- 公式分数变化会更新当前阶段
- 公式分数独立存储在数据库中

### 4.6 等级激活经验值机制（2026-01-23 新增）

#### 功能概述
- 每个等级配置有独立的激活经验值 `activate_exp_count`
- 玩家购买凭证道具后，自动获得对应的激活经验值
- 激活经验值会影响当前阶段的计算，可能立即解锁新的阶段奖励

#### 实现方式：动态计算
采用**动态计算**方式，不存储激活经验值，每次计算总分时实时遍历：
```java
public long getTotalScore() {
    long activateExp = 0;

    // 遍历所有等级配置
    List<RefActivityFundLevel> levelList = RefActivityFundLevel.getMgr().getLevelListByFundId(getFundId());
    for (RefActivityFundLevel levelRef : levelList) {
        // 检查是否拥有该等级的凭证道具
        if (hasDistinguishItem(levelRef)) {
            activateExp += levelRef.activate_exp_count;
        }
    }

    return _m_taskScore + _m_formulaScore + activateExp;
}
```

#### 设计优势
1. **无需存储**：不需要数据库字段和内存字段存储激活经验值
2. **自动生效**：购买凭证道具后，下次计算总分时自动生效
3. **无需去重**：通过检查凭证道具是否存在天然去重
4. **逻辑简单**：代码清晰易维护，无需额外的事件监听

#### 使用示例
```
等级1配置：activate_exp_count = 1000, last_step = 10, distinguish_item = item:1001:1
等级2配置：activate_exp_count = 2000, last_step = 20, distinguish_item = item:1002:1

玩家购买等级1凭证（item:1001）：
  - 下次计算getTotalScore()时，检测到拥有item:1001
  - 自动累加 1000 激活经验值
  - 当前阶段自动更新（updateStep调用getTotalScore）

玩家购买等级2凭证（item:1002）：
  - 下次计算getTotalScore()时，检测到拥有item:1002
  - 自动累加 2000 激活经验值
  - 当前阶段自动更新
```

#### 注意事项
1. **性能考虑**：等级配置数量一般较少（通常3-5个），遍历开销可忽略
2. **凭证检查**：`hasDistinguishItem()` 方法检查玩家背包是否拥有凭证道具
3. **自动生效**：所有调用 `getTotalScore()` 的地方都会自动计算激活经验值
4. **无需推送**：购买凭证道具本身会触发道具变化推送，客户端自然会刷新界面

### 4.7 任务轮次刷新机制（2026-01-21 新增）

#### 功能概述
- 当配置了 `task_refresh_time` 字段（大于0）时，系统将自动按轮次刷新任务进度
- 以活动开启时间为基准，每隔 `task_refresh_time` 秒为一轮
- 轮次变更时，自动清除玩家的任务计数和完成次数

#### 轮次计算规则
```
活动开启时间：activityStartTimeMs
当前时间：nowMs
刷新间隔：task_refresh_time（秒）

经过时间（毫秒）= nowMs - activityStartTimeMs
当前轮次号 = (经过时间 / (刷新间隔 * 1000)) + 1
```

**示例**：
- 活动在 1:00 开启
- task_refresh_time = 3600（1小时）
- 2:00 时：轮次号 = 2
- 3:00 时：轮次号 = 3

#### 重置时机
任务数据在以下两个时机检查并重置：
1. **任务事件触发时**：在 `ActivityFundTaskInfo.onLogicEvt()` 中调用 `ActivityFundInfo.checkAndResetExpiredTasks()`
2. **查询任务列表时**：在 `MsgDealer_GC2GS_017_019_ReqActivityFundTaskInfo` 中调用 `ActivityFundInfo.checkAndResetExpiredTasks()`

#### 数据库字段
主表（player_activity_fund）新增字段：
- `activity_start_time_ms`（long）：活动开始时间（毫秒，永久基金为0）
- `last_refresh_round`（long）：记录上次刷新时的轮次号

任务表（player_activity_fund_task）：
- **不存储**轮次号字段，由主表统一管理

#### 重置逻辑（优化后）
```java
// 在 ActivityFundInfo.checkAndResetExpiredTasks() 中
if (lastRefreshRound < currentRound) {
    // 收集所有任务的数据库ID
    List<Long> dbIds = new ArrayList<>();
    for (ActivityFundTaskInfo taskInfo : taskList) {
        if (taskInfo.getDbId() != 0) {
            dbIds.add(taskInfo.getDbId());
        }
        // 重置内存对象：dbId=0, currentCount=0, finishedTimes=0
        taskInfo.resetToInitState();
    }
    
    // 批量删除数据库记录（使用 delAllInList 方法）
    if (!dbIds.isEmpty()) {
        getBM().getBM(PlayerActivityFundTaskBO.class).delAllInList("id", dbIds);
    }
    
    // 更新轮次号
    lastRefreshRound = currentRound;
    // 保存到主表数据库
}
```

#### 使用场景
- 每日刷新任务：task_refresh_time = 86400（24小时）
- 每小时刷新任务：task_refresh_time = 3600（1小时）
- 不刷新任务：task_refresh_time = 0（默认）

#### 注意事项
1. **仅活动基金支持**：常驻基金（activityInstanceId=0, activityStartTimeMs=0）不支持轮次刷新
2. **不使用tick**：采用被动检查机制，避免性能开销
3. **线程安全**：检查和重置操作在玩家锁保护下执行
4. **批量删除优化**：使用 `delAllInList` 批量删除任务记录，避免逐条删除
5. **活动开始时间存储**：在创建基金时通过 `_AActivityBase.getStartTimeMs()` 获取并存储

- 懒加载数据库插入（只在有数据变化时才插入，dbId=0表示未插入）
- 总分 = taskScore(任务分数) + formulaScore(公式分数) + activateExp(激活经验值)
- 公式分数独立存储，通过事件刷新
- 激活经验值动态计算，不存储（遍历等级检查凭证道具）

### 5.4 关键算法

#### 计算当前阶段

**算法思路**：
1. 按 `need_count` 升序遍历 `activity_fund_step` 表
2. 找到最后一个 `need_count <= totalScore` 的阶段作为当前阶段
3. 若 `last_step = -1` 表示无上限等级，允许无限扩展

**示例**：
```
阶段1：需要分数 >= 100
阶段2：需要分数 >= 300
阶段3：需要分数 >= 600
玩家分数 = 500
结果：当前阶段 = 2
```

#### 一键领取逻辑（按等级遍历，一次只处理一个等级）

**执行步骤**：
1. **计算可领取区间**：`min(已领免费档, 已领付费档) + 1` 到 `当前阶段`
2. **按等级顺序遍历**：获取所有等级配置，从低等级到高等级依次检查
3. **找到第一个未完成等级**：
   - 检查当前等级是否完成（免费档和付费档都必须达到 `last_step`）
   - 如果已完成，继续检查下一个等级
   - 如果未完成，进入步骤4
4. **处理当前等级**：
   - 计算该等级包含的阶段范围（`前一个等级的last_step + 1` 到 `当前等级的last_step`）
   - 在该范围内收集奖励：
     - **免费档**：直接收集，无需凭证
     - **付费档**：检查是否拥有该等级的凭证道具，有则收集，无则跳过
5. **更新记录**：更新已领取阶段，保存数据库，推送协议
6. **结束**：处理完当前等级后立即结束，不继续处理下一个等级

**设计特点**：
- **一次只处理一个等级**：确保玩家按等级顺序推进
- **免费档独立**：没有购买付费凭证的玩家也能正常领取所有等级的免费档
- **简化逻辑**：无需复杂的前置等级检查，直接判断当前等级是否完成

### 5.5 事件监听

#### 任务触发事件

- 根据 `activity_fund_task.trigger_event` 配置监听事件
- 事件触发时检查 `trigger_condition` 条件
- 根据 `trigger_count_rate` 计算增量值

#### 公式分数刷新事件

- 更新当前阶段

## 9. 等级系统详细设计（2024-01-15 新增）

### 9.1 配表设计

#### activity_fund_level 表

| 字段 | 类型 | 说明 |
|------|------|------|
| id | long | 唯一ID |
| activity_id | long | 活动ID |
| level | int | 等级（从1开始递增） |
| last_step | int | 该等级的最后一个阶段，-1表示无上限 |
| distinguish_item | string | 凭证道具（拥有此道具可领取该等级的付费档） |

**配置示例**：
```
id  activity_id  level  last_step  distinguish_item
1   1001         1      10         item:1001:1    # level 1 包含 step 1-10，需要道具1001
2   1001         2      20         item:1002:1    # level 2 包含 step 11-20，需要道具1002
3   1001         3      -1         item:1003:1    # level 3 包含 step 21+（无上限），需要道具1003
```

### 9.2 核心逻辑

#### 等级查找算法（getLevelByStep）

**算法思路**：
1. 等级数据已按 `level` 排序
2. 遍历等级列表，查找包含目标 `step` 的等级
3. 判断规则：
   - 如果 `last_step = -1`：表示无上限等级，直接返回
   - 如果 `last_step < step`：记录该等级，继续查找
   - 如果 `last_step >= step`：找到包含该 `step` 的等级，返回
4. 若遍历结束，返回最后一个记录的等级（兜底）

**示例**：
```
等级1：last_step = 10
等级2：last_step = 20
等级3：last_step = -1

查找 step = 15：
- 等级1：10 < 15，记录等级1，继续
- 等级2：20 >= 15，返回等级2

查找 step = 25：
- 等级1：10 < 25，记录等级1，继续
- 等级2：20 < 25，记录等级2，继续
- 等级3：-1 < 0，返回等级3（无上限）
```

### 9.3 领取流程

#### 一键领取逻辑（按等级遍历，一次只处理一个等级）

**流程图**：

```
开始
  ↓
计算可领取区间：[min(已领免费档,已领付费档)+1, 当前阶段]
  ↓
获取所有等级配置（已按level排序）
  ↓
遍历等级列表，从低到高
  ↓
┌─────────────────────────────────┐
│检查当前等级是否完成？                 │
│  条件：免费档>=last_step AND        │
│        付费档>=last_step            │
└─────────────────────────────────┘
         ↓是
  跳过该等级，继续下一个等级 ←────────┐
         ↓否                        │
计算该等级的阶段范围                 │
  ↓                                 │
在该范围内收集奖励：                 │
  - 免费档：直接收集                 │
  - 付费档：有凭证则收集             │
  ↓                                 │
更新已领取阶段记录                   │
  ↓                                 │
处理完，结束 ←─────────────────────┘

发放奖励，保存数据库，推送协议
  ↓
结束
```

**执行要点**：
1. **等级顺序处理**：严格按照等级顺序推进，不允许跳级
2. **一次性处理**：找到第一个未完成的等级后，立即处理并结束
3. **免费档独立**：没有凭证的玩家可以持续领取免费档，付费档跳过
4. **多次领取**：玩家需要多次点击才能完成所有等级的奖励领取

### 9.4 关键设计特点

1. **按等级顺序完成**
   - 严格按照等级顺序处理，不允许跳级
   - 必须完成当前等级的免费档和付费档才能进入下一等级
   - 无凭证玩家可以持续领取免费档，但无法领取付费档

2. **一次只处理一个等级**
   - 找到第一个未完成的等级后立即处理
   - 处理完后立即结束，不继续处理下一个等级
   - 玩家需要多次点击才能完成所有等级的奖励

3. **免费档独立推进**
   - 没有购买付费凭证的玩家也能正常领取所有等级的免费档奖励
   - 免费档和付费档互不影响，可以独立推进
   - 付费档需要凭证才能领取，无凭证时自动跳过

4. **无上限等级支持**
   - `last_step = -1` 表示无上限等级
   - 允许最高等级无限扩展阶段
   - 支持长期运营的活动

5. **逻辑简单清晰**
   - 删除复杂的前置等级检查算法
   - 直接检查当前等级是否完成（免费档>=last_step AND 付费档>=last_step）
   - 通过等级遍历自然实现顺序控制

## 10. 注意事项

1. **分数不会被消耗**：领取奖励不会扣除分数，分数只用于判断阶段和是否可以领取
2. **阶段不存储**：阶段通过分数实时计算，不需要单独存储在数据库
3. **一键领取**：客户端请求领取时，按等级顺序处理，找到第一个未领完的等级并处理该等级的所有可领取阶段（一次只处理一个等级）
4. **已领取记录**：使用单个int记录最大已领取阶段号，小于等于此值的阶段视为已领取
5. **等级凭证系统**：每个等级有独立的凭证道具，领取时根据阶段所属等级的凭证道具判断是否发放付费档奖励
6. **任务可重复**：任务可以多次完成，受 `task_finish_limit` 限制
7. **线程安全**：所有操作需要在玩家锁 `getUserData().lockUser()` 内执行
8. **活动实例**：每个活动基金对应一个 `activityInstanceId`，支持多个基金同时存在
9. **公式分数独立**：公式分数独立存储，通过事件刷新，与任务分数分开管理
10. **等级系统**（重要）：
    - 阶段通过 `last_step` 分组到不同等级
    - 玩家必须同时完成当前等级的免费档和付费档才能进入下一等级
    - 无凭证玩家无法进入下一等级（必须购买凭证）
    - 支持无上限等级（last_step=-1），允许无限扩展最高等级
    - 一次只处理一个等级，处理完后结束，确保玩家按等级顺序推进
